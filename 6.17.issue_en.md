# 2026-06-17 Scout Mini Gazebo Navigation Issue Record

## Issue 1: Missing Executables in Launch File
**Symptom**: `ros2 launch` failed with `executable 'tf_static_relay.py' not found` and multiple `NameError` exceptions (undefined variables).

**Cause**: 
- Some Python scripts lacked execute permissions and were not properly installed via CMake.
- Launch file had duplicate or missing node definitions due to repeated edits causing broken variable references.

**Resolution**:
- Added `tf_static_relay.py` to CMakeLists.txt install rules.
- Reorganized all node definitions in the launch file to ensure every node variable is defined before use.
- Restored accidentally removed `model_prefix_tf_odom` and `model_prefix_tf_base_link` static TF publisher nodes.

**Status**: ✅ Resolved

---

## Issue 2: TF Frame Name Mismatch (Gazebo vs ROS)
**Symptom**: Gazebo published odom with frame `scout_mini/odom` while ROS expects `odom`. Same prefix issue for base_link, causing RViz unable to display robot pose and map correctly.

**Cause**: Gazebo simulation runs under model name `scout_mini`, automatically prefixing all frames with `scout_mini/`.

**Resolution**:
- Added two `static_transform_publisher` nodes publishing identity transforms (0,0,0,0,0,0):
  - `odom` → `scout_mini/odom`
  - `scout_mini/base_link` → `base_link`
- Applied `use_sim_time:=true` to all bridge nodes.
- Added identity transforms for LiDAR sensors (`front_lidar_link` ↔ `scout_mini/base_link/front_lidar_sensor`, etc.).

**Status**: ✅ Resolved

---

## Issue 3: Reversed Rotation Direction (Gazebo left / RViz right)
**Symptom**: When commanding a left turn via keyboard, the robot physically turned left in Gazebo but RViz displayed a right turn.

**Cause**: Left/right wheel joints were incorrectly assigned in the DiffDrive plugin, causing inverted angular velocity sign.

**Resolution**:
- Correctly assigned wheel joints:
  - `<left_joint>`: `front_left_wheel` + `rear_left_wheel`
  - `<right_joint>`: `front_right_wheel` + `rear_right_wheel`
- Set `wheel_separation: -${track}` (negative sign flips angular velocity back to correct direction).

**Status**: ✅ Resolved

---

## Issue 4: Rotation Rate Mismatch (Gazebo vs RViz scaling)
**Symptom**: The robot's physical rotation angle in Gazebo was not proportional to the pose rotation displayed in RViz, with ~1.3x to 1.8x magnification.

**Cause**: `wheel_radius` parameter was far larger than the actual tire radius. The original value `0.145m` (diameter 290mm) was approximately 2x the Scout Mini's actual tire. The DiffDrive plugin computes both linear and angular velocity based on this parameter, so an oversized radius inflates all odometry output.

**Resolution** (multi-round calibration):
| Step | wheel_radius | Error Ratio | Action |
|------|-------------|-------------|--------|
| 1 | 0.145 → 0.085 | ~1.7x | Initial large reduction |
| 2 | 0.085 → 0.064 | ~1.33x (135°→180°) | Scaled by 135/180 = 0.75 |
| 3 | 0.064 → 0.058 | ~1.11x (90°→100°) | Scaled by 90/100 = 0.9 |

**Current value**: `wheel_radius = 0.058m` (diameter ~116mm), spawn height adjusted to `0.118m`.

**Status**: ✅ Nearly aligned, error reduced to ~10%. Further fine-tuning possible (rule: smaller `wheel_radius` = slower RViz rotation).

## Issue 5: Poor SLAM Rotation Mapping Accuracy
**Symptom**: The SLAM-generated map showed significant drift and jumps during rotation, with violent map→odom transform oscillations.

**Cause**:
- LiDAR update rate was only 5Hz (200ms/frame), causing severe motion distortion during rotation.
- SLAM correction trigger thresholds were too high, skipping scan matching for small rotations.
- Scan matching precision parameters were too coarse.

**Resolution**:

### 5.1 Increased LiDAR Update Rate
- [scout_mini_gazebo.xacro](src/scout_mini_dual_lidar_gazebo/urdf/scout_mini_gazebo.xacro): front and rear LiDAR `update_rate` from **5Hz → 20Hz**.

### 5.2 SLAM Parameter Tuning
Modified [slam_toolbox_params.yaml](src/scout_mini_dual_lidar_gazebo/params/slam_toolbox_params.yaml):

| Parameter | Old | New | Description |
|-----------|-----|-----|-------------|
| minimum_travel_heading | 0.3 | 0.15 | Trigger rotation correction at ~8.6° |
| minimum_time_interval | 0.5 | 0.2 | More frequent scan matching |
| map_update_interval | 3.0 | 1.0 | More timely map updates |
| lstep / astep | 0.05 | 0.01 | Finer pose optimization |
| iterations | 10 | 15 | More convergence iterations |
| correlation_search_space_dimension | 0.5 | 0.3 | Finer search grid |
| srr / str | 0.01 | 0.005 | Higher trust in Gazebo ideal odometry |
| srt / stt | 0.02 | 0.01 | Lower noise assumption |

### 5.3 Odometry Publishing Frequency
- DiffDrive plugin `odom_publish_frequency` from 50Hz → **100Hz**.

### 5.4 Dual LiDAR Fusion
- Created [laser_merger.py](src/scout_mini_dual_lidar_gazebo/src/laser_merger.py) that uses TF transforms to merge point clouds from both 360° LiDARs into the `base_link` frame, publishing `/merged/scan` for SLAM, achieving complete 360° environmental perception.

**Status**: ✅ Resolved, rotation mapping quality significantly improved.

## Summary
This work resolved three major categories of issues with Scout Mini in Gazebo simulation:
1. **Startup & Configuration**: Missing executables, undefined variables, TF frame mismatches.
2. **Kinematic Calibration**: Rotation direction fix + wheel radius calibration (0.145→0.058), aligning odometry with physical motion.
3. **SLAM Optimization**: LiDAR frequency boost, scan matching parameter tuning, dual LiDAR fusion, odometry frequency boost.

Key files modified:
- `urdf/scout_mini_gazebo.xacro`: wheel radius, LiDAR frequency, DiffDrive config
- `launch/scout_mini_gazebo.launch.py`: TF bridges, node registration, spawn height
- `params/slam_toolbox_params.yaml`: SLAM correction frequency & precision parameters
- `src/laser_merger.py`: new dual LiDAR fusion node
