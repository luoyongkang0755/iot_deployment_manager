# Scout Mini Gazebo Simulation Issue Record

## Issue 1: Xacro Parsing Error `Undefined parameters [0,0]`

**Symptom**: `Undefined parameters [0,0] when instantiating macro: scout_wheel_type1` on launch.

**Root Cause**: The default parameter value `collision_rpy:=0 0 0` in `scout_wheel_type1.xacro` and `scout_wheel_type2.xacro` was not quoted. The xacro parser interpreted the trailing `0 0` after the space as additional undefined parameter names.

**Status**: Resolved — Changed `collision_rpy:=0 0 0` to `collision_rpy:='0 0 0'` in both wheel xacro files.

---

## Issue 2: Wheel Rotation Axis Wrong (Rotating Around X Instead of Y)

**Symptom**: Wheels spun around the wrong axis (X-axis instead of Y-axis).

**Root Cause**: The URDF wheel joint axis was set to `"0 0 1"` (Z-axis). For forward-rolling differential drive robots, the correct axis is Y.

**Status**: Resolved — Changed all 4 wheel `axis_xyz` to `"0 -1 0"` (Y-axis).

---

## Issue 3: Wheels Sinking Into the Ground

**Symptom**: Wheels sank halfway into the ground as soon as the robot started moving.

**Root Cause**:
1. The `base_footprint_joint` z-offset only used `${-wheel_radius}` (-0.145), but the wheel center also has `wheel_vertical_offset = -0.060`, causing the wheel bottoms to be 60mm below ground level.
2. The collision cylinder was oriented along the Z-axis (vertical) by default, when it should be along the Y-axis (horizontal) to match the wheel shape, preventing the physics engine from properly detecting ground contact.

**Status**: Resolved — 
1. Changed `base_footprint_joint` z-offset from `${-wheel_radius}` to `${wheel_vertical_offset - wheel_radius}`.
2. Added `collision_rpy="1.5708 0 0"` to all 4 wheels to rotate the collision cylinder from vertical to horizontal.

---

## Issue 4: Keyboard Control Direction Errors

**Symptom**:
- Pressing "i" moved backward (first fix: all axis="0 -1 0" fixed forward, but turning broke)
- Pressing "j" sometimes turned left, sometimes right, sometimes forward

**Attempts**:
1. First: All wheels axis="0 1 0" → i went backward, j turn left correct
2. Second: All wheels axis="0 -1 0" → i went forward correct, j turned right (reversed)
3. Third: Left axis="0 1 0", right axis="0 -1 0" → i turned right, j went forward (completely broken)

**Final Resolution**: Used uniform axis="0 -1 0" for all wheels, and swapped `left_joint`/`right_joint` in the DiffDrive plugin (changed left from front_left+rear_left to front_right+rear_right) to fix the turning direction.

**Status**: Resolved.

---

## Issue 5: SLAM Not Producing Map Data

**Symptom**: slam_toolbox ran on startup but produced no map data.

**Root Cause**: The SLAM parameter file had `scan_topic: /scan`, but laser scan topics were published at `/front/scan` and `/rear/scan`. The `/scan` topic did not exist.

**Status**: Resolved — Changed `scan_topic` from `/scan` to `/front/scan` in `slam_toolbox_params.yaml`, and corrected the QoS override topic name.

---

## Issue 6: Gazebo Bridge Message Type Inconsistency

**Symptom**: Odometry and TF data potentially not bridging correctly from Gazebo to ROS.

**Root Cause**: The bridge arguments in `scout_mini_gazebo.launch.py` mixed `ignition.msgs.*` and `gz.msgs.*` namespaces:
- `/odom`, `/tf`, `/joint_states` used `ignition.msgs.*`
- `/clock`, `/cmd_vel`, laser scans used `gz.msgs.*`

**Status**: Resolved — Unified all bridge message types to `gz.msgs.*`.

---

## Issue 7: SLAM Pose Not Updating (Ghosting Artifacts) ⚠️ UNRESOLVED

**Symptom**: Laser scanners work continuously, SLAM publishes maps, but the robot pose never updates. All scan frames are incorrectly stacked at the same origin position, creating repeated "ghost" obstacle rings.

**Diagnosis**:
- TF tree structure is correct: `odom → scout_mini/odom → scout_mini/base_link → base_link`
- Dynamic part `scout_mini/odom → scout_mini/base_link` updates at 50Hz
- `/odom` topic has data
- `/tf` topic has DiffDrive-published dynamic transforms

**Attempted Fixes**:
1. Added `transform_timeout: 0.5` and `transform_tolerance: 0.1` to SLAM params to address timing race conditions
2. Created `tf_static_relay.py` node to forward `/tf_static` to `/tf`, consolidating all transforms onto a single TF channel

**Hypothesized Root Cause**: `robot_state_publisher` publishes static transforms to `/tf_static`, while Gazebo DiffDrive publishes dynamic transforms to `/tf`. When slam_toolbox (in synchronous mode) looks up `odom → base_link`, the separation across two TF channels may cause compatibility issues preventing the full chain from being assembled, making SLAM believe the robot is stationary.

**Status**: UNRESOLVED — pending verification.
