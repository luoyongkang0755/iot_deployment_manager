# Scout Mini Gazebo Simulation Issue Record

## Issue 1: Xacro Parsing Error `Undefined parameters [0,0]`

**Symptom**: Error `Undefined parameters [0,0] when instantiating macro: scout_wheel_type1` when launching `scout_mini_gazebo.launch.py`.

**Root Cause**: The default parameter value `collision_rpy:=0 0 0` in `scout_wheel_type1.xacro` and `scout_wheel_type2.xacro` was not quoted. The xacro parser misinterpreted the trailing `0 0` after the space as additional undefined parameter names.

**Resolution**: Wrapped the default value in single quotes in both wheel xacro files: `collision_rpy:='0 0 0'`. Later changed to `collision_rpy:=&quot;${M_PI/2} 0 0&quot;` to make the collision cylinder lie sideways by default.

**Status**: ✅ Resolved

## Issue 2: Wheel Rotation Axis Direction Confusion

**Symptom**: Wheel rotation axis was repeatedly incorrect—forward/backward and left/right turn directions were wrong after multiple attempts.

**Attempts**:
1. All wheels `axis="0 1 0"` → pressing i moved backward (reversed)
2. All wheels `axis="0 -1 0"` → pressing i moved forward, pressing j turned right (reversed)
3. Left wheels `axis="0 1 0"`, right wheels `axis="0 -1 0"` → completely broken: i turned right, j moved forward
4. Right wheels with `rpy="3.14 0 0"` flipped 180°, then both sides shared axis `(0, -1, 0)` → DiffDrive sent opposite speeds but physically both sides rotated the same direction

**Root Cause**: Under the Y-axis scheme, after flipping the right wheels 180°, both left and right wheel axes became the same direction. Opposite speeds from DiffDrive resulted in same-direction physical rotation, turning straight-line movement. Meanwhile, the keyboard control's differential mapping (which side is faster determines turn direction) must be consistent with the physical axis direction.

**Final Resolution (tentative)**: Swapped `left_joint` and `right_joint` in the DiffDrive plugin (`left_joint=rear_right_wheel`, `right_joint=rear_left_wheel`) to fix the right-turn issue when pressing j.

**Status**: Resolved

## Issue 3: Wheels Sinking Into the Ground

**Symptom**: Wheels sank halfway into the ground as soon as the robot started moving.

**Root Cause**:
1. The `base_footprint_joint` z-offset only used `${-wheel_radius}` (-0.145), but the wheel center also has `wheel_vertical_offset = -0.060`
2. The collision cylinder was not correctly oriented sideways, preventing the physics engine from detecting ground contact

**Resolution**:
1. Changed `base_footprint_joint` z-offset to `${wheel_vertical_offset - wheel_radius}`
2. Set collision body `collision_rpy="${M_PI/2} 0 0"` to lay the cylinder sideways matching the wheel shape

**Status**: ✅ Resolved

## Issue 4: Front Wheel Mimic Joints Causing Oscillation

**Symptom**: When using mimic joints for four-wheel drive, the robot oscillated back and forth and could not stabilize.

**Attempts**:
1. DART engine + mimic → back-and-forth oscillation
2. ODE engine + mimic → still oscillating
3. Removed mimic, only driving rear wheels → oscillation disappeared

**Root Cause**: Gazebo Ignition Fortress has incomplete support for URDF `<mimic>` joints; force transmission is unstable.

**Temporary Workaround**: Removed mimic joints; DiffDrive only drove the two rear wheels. However, this led to poor turning performance.

**Status**: ⚠️ Temporarily worked around; later changed to four-wheel direct drive (see Issue 11)

## Issue 5: Turning Stuck at 90 Degrees

**Symptom**: The robot could rotate but got completely stuck at around 90 degrees and couldn't continue turning. Wheels kept spinning but the body didn't move, only suddenly breaking through after a long delay.

**This was the project's most core and time-consuming issue.**

### Methods tried:

1. **Tuning friction parameters mmu/mu2**:
   - `mu=1.0, mu2=0.5` → slow but could turn
   - `mu=10.0, mu2=0.01` → extreme asymmetry, immediately unable to turn
   - `mu=3.0, mu2=0.15` → rear wheels dragged along, moved forward instead
   - `mu=1.5, mu2=0.8` → some effect but stuck when transitioning from lateral to longitudinal

2. **Adding slip1/slip2 parameters**:
   - `slip1=0.01, slip2=0.5` → symmetric friction + lateral slip, successful rotation but stuck laterally
   - `slip1=0.01, slip2=1.0` → some improvement with mu2=0.2
   - `slip1=0, slip2=1.0` → zero forward slip, worse than the previous small slip

3. **Tuning contact stiffness kd/kp**:
   - `kd=1e6, kp=1e6` → too stiff
   - `kd=1000, kp=100000` → moderate
   - `kd=100, kp=50000` → too soft, worse results
   - `kd=50, kp=50000` → softer approach
   - `kd=10, kp=10000` → extremely soft, wheels sank into ground

4. **Switching physics engines**:
   - ODE + quick solver + cfm/erp → usable but with stuttering
   - DART + dantzig solver → mimic oscillation problem
   - ODE without cfm/erp, using defaults → simplified approach

5. **TF tree fixes**:
   - Discovered missing `scout_mini/base_footprint → base_footprint` bridge
   - 90-degree stuck issue persisted after adding it
   - Removed redundant `base_footprint` bridge (due to dual-definition conflict)

6. **Swapping left/right joints**:
   - `left_joint=rear_right_wheel, right_joint=rear_left_wheel` → fixed right-turn on j press

7. **Comparing ugv_gazebo_sim open-source project**: Found key differences in its successful approach—four-wheel direct drive, Z-axis, no custom friction parameters.

**Final Solution (in progress)**: Adopted ugv_gazebo_sim's four-wheel direct drive + Z-axis scheme, removed all custom friction parameters.

**Status**: 🔄 Rework completed, successful

## Issue 9: Invalid Wheel Inertia

**Symptom**: Gazebo reported `A link named front_left_wheel_link has invalid inertia`.

**Root Cause**: Cylinder inertia must satisfy the triangle inequality `Ixx + Izz >= Iyy`. The previously manually-set inertia values `ixx=0.001, iyy=0.003, izz=0.001` violated the physics constraint.

**Resolution**: Recalculated using cylinder inertia formulas:
- `mass=1.5kg, r=0.145m, h=0.1m`
- `ixx = izz = m/12 × (3r² + h²) = 0.0091`
- `iyy = m × r²/2 = 0.0158`

**Status**: ✅ Resolved

## Issue 11: Comprehensive Overhaul Inspired by ugv_gazebo_sim

**Background**: Analyzed the successfully-running `h3ct0r/ugv_gazebo_sim` Scout Mini simulation project on GitHub and identified core differences:

| Comparison | Our Old Approach | ugv_gazebo_sim |
|-----------|-----------------|----------------|
| Drive method | Rear-wheel drive + front mimic | **All four wheels direct drive** |
| Wheel axis | Y-axis + rpy flip | **Z-axis** (`0 0 1` / `0 0 -1`) |
| Friction params | Extensive custom mu/mu2/slip/kd/kp | **None at all**, engine defaults |
| Physics engine | ODE/DART switching + cfm/erp/iters | ODE default parameters |

**Changes**:
1. Removed all mimic joints, four wheels independently driven
2. Unified axis to Z-axis: left wheels `axis="0 0 1"` joint `rpy="-1.57 0 0"`, right wheels `axis="0 0 -1"` joint `rpy="1.57 0 0"`
3. DiffDrive drives all four joints (`left_joint` specifies `front_left_wheel` + `rear_left_wheel`, same for `right_joint`)
4. Deleted all wheel `<surface>`/`<friction>`/`<contact>` custom parameters
5. Deleted ground friction/contact custom parameters
6. Simplified world physics config (removed cfm/erp/solver iters)
7. Added `max_wheel_torque=20` and `max_linear_acceleration=1.0`
8. Added `collision_rpy` parameter support to wheel macros

**Status**: 🔄 Rework completed, successful

## Issue 12: World Plugin Conflict — Gazebo Blank / Robot Not Moving / No Lidar Data

**Symptom (one of three)**:
- No plugins declared → robot can move, but lidar has no data
- Only Sensors declared → Gazebo completely blank
- Sensors + SceneBroadcaster declared → lidar has data, GUI normal, but robot won't move

### Attempted Process

1. Keep Sensors + SceneBroadcaster → robot won't move (missing Physics and Contact)
2. Keep Sensors + SceneBroadcaster + Contact → still won't move (still missing Physics)
3. Add Physics → robot can move but lidar fails again? etc.

### Root Cause

Ignition Fortress's `server.config` loads Physics + UserCommands + SceneBroadcaster by default. **Once any explicit `<plugin>` declarations appear in the world file, Gazebo stops loading default plugins and only loads the explicitly declared ones.** So all 5 required plugins must be explicitly declared.

Additionally, the original file used `gz-sim-*` naming, but Ignition Fortress actually recognizes `ignition-gazebo-*`.

### Final Solution

Explicitly declared all 5 system plugins in `simple_test_world.world`:

```xml
<plugin filename="ignition-gazebo-sensors-system" name="gz::sim::systems::Sensors"> ... </plugin>
<plugin filename="ignition-gazebo-scene-broadcaster-system" name="gz::sim::systems::SceneBroadcaster"> </plugin>
<plugin filename="ignition-gazebo-user-commands-system" name="gz::sim::systems::UserCommands"> </plugin>
<plugin filename="ignition-gazebo-contact-system" name="gz::sim::systems::Contact"> </plugin>
<plugin filename="ignition-gazebo-physics-system" name="gz::sim::systems::Physics"> </plugin>
```

**Status**: ✅ Resolved

## Issue 13: Gazebo Model Name Prefix Breaking TF Tree

**Symptom**: Gazebo's diff drive plugin automatically added the model name prefix `scout_mini/` when publishing TF:
- `scout_mini/odom → scout_mini/base_footprint` (Gazebo published)
- `base_link → base_footprint → front_lidar_link` (robot_state_publisher published)

Two TF subtrees were completely independent with no connection point. In RViz the Fixed Frame dropdown only had `scout_mini/odom` without `odom`, the robot model didn't display, and SLAM couldn't work.

### Attempted Process

1. Tried setting diff drive's `odom_frame` to unprefixed `odom` → Gazebo still auto-added the prefix, ineffective
2. Tried remapping topics → ineffective, this was a TF frame_id issue not a topic name issue

### Final Solution

Added two identity static TF transforms bridging the two trees:

```
odom  →  scout_mini/odom           (identity, static)
scout_mini/base_footprint  →  base_footprint   (identity, static)
```

Complete TF chain:
```
map → odom → scout_mini/odom → scout_mini/base_footprint → base_footprint → base_link → sensors
```

**Key Finding**: The diff drive plugin configured `<robot_base_frame>base_footprint</robot_base_frame>` in the xacro, so Gazebo actually published `scout_mini/base_footprint`, not `scout_mini/base_link`. We had been incorrectly bridging `scout_mini/base_link → base_link`, connecting a non-existent frame.

**Status**: ✅ Resolved

## Issue 14: ROS-Gazebo Bridge Message Type Namespace Inconsistency

**Symptom**: `/odom` and `/tf` bridges may not work correctly.

### Root Cause

Two namespaces were mixed in `scout_mini_gazebo.launch.py`:
- `/cmd_vel@geometry_msgs/msg/Twist]gz.msgs.Twist` (`gz.msgs` prefix)
- `/odom@nav_msgs/msg/Odometry[ignition.msgs.Odometry` (`ignition.msgs` prefix)

Actual message types published by Gazebo: `ign topic -i -t /odom` shows `ignition.msgs.Odometry`, `ign topic -i -t /tf` shows `ignition.msgs.Pose_V`.

### Final Solution

Unified rule: ROS→Gazebo use `]gz.msgs.*`, Gazebo→ROS use `[ignition.msgs.*`:

```python
'/cmd_vel@geometry_msgs/msg/Twist]gz.msgs.Twist',
'/odom@nav_msgs/msg/Odometry[ignition.msgs.Odometry',
'/tf@tf2_msgs/msg/TFMessage[ignition.msgs.Pose_V',
'/joint_states@sensor_msgs/msg/JointState[ignition.msgs.Model',
'/front/scan@sensor_msgs/msg/LaserScan[gz.msgs.LaserScan',
'/rear/scan@sensor_msgs/msg/LaserScan[gz.msgs.LaserScan',
```

**Status**: ✅ Resolved

## Issue 18: LiDAR Static TF Offset Causing LaserScan Display at Wrong Position

**Symptom**: In RViz, LaserScan did not display around the robot, appearing offset to an incorrect position.

### Root Cause

The LiDAR static TF in `scout_mini_gazebo.launch.py` had an offset of `0.245, 0, 0.14`. But the Gazebo sensor was already placed under `<gazebo reference="front_lidar_link">` with `<pose>0 0 0 0 0 0</pose>`, so the sensor frame in Gazebo was already at the URDF link position. The redundant static TF offset caused the laser data to be offset by 2x the distance.

### Final Solution

Changed both front and rear LiDAR static TFs to identity transforms (all zeros):
```
front_lidar_link  →  scout_mini/base_link/front_lidar_sensor  (0,0,0,0,0,0)
rear_lidar_link   →  scout_mini/base_link/rear_lidar_sensor   (0,0,0,0,0,0)
```

**Status**: ✅ Resolved

## Lessons Learned

1. **Skid-steer turning is a known hard problem in the ODE physics engine** — line contact between cylinder colliders and flat ground cannot generate sufficient lateral force differential to drive turning.
2. **Friction parameter tuning was a dead end**: repeatedly adjusting mu/mu2/slip/contact parameters only fine-tuned behavior, unable to resolve fundamental physics simulation limitations.
3. **Mimic joints are unreliable in Ignition Fortress**: avoid using them; use multi-joint direct drive instead.
4. **Studying successful reference cases is far more efficient than blind trial-and-error**: ugv_gazebo_sim's four-wheel direct drive + Z-axis + no custom friction parameter approach is a proven viable path.
5. **Dual-source TF tree conflict (DiffDrive dynamic + URDF static both defining base_footprint) was a possible root cause of the 90-degree stuck issue**.
6. **Z-axis is more suitable for DiffDrive plugin than Y-axis**: the Z-axis scheme doesn't need rpy flipping, and left/right direction mapping is more intuitive and reliable.
7. **Explicit world plugin declarations suppress default loading**: all required plugins (Physics, Contact, Sensors, SceneBroadcaster, UserCommands) must be explicitly declared, and must use `ignition-gazebo-*` naming.
8. **Gazebo model name prefix issue (`scout_mini/`)**: diff drive and other plugins auto-add the model name prefix to frame_ids, requiring static TF bridges to standard ROS coordinate frames.
9. **Static TFs should be identity transforms**: when Gazebo sensors are already placed at the URDF link position (`<pose>0 0 0 0 0 0</pose>`), the bridging static TF must be all zeros.
10. **diff drive's `robot_base_frame` determines the correct connection point in the TF tree**: if set to `base_footprint` in the xacro, the bridge must target `base_footprint`, not `base_link`.
11. **Duplicate node name conflict (`robot_state_publisher`)**: Nav2 yaml config must not contain node configurations that duplicate those in the Gazebo simulation.
12. **SLAM's `map_name` should stay as default `map`**: avoid inconsistency with Nav2's default topic names.
